# Version 1.3: hiding controllers (HidHide) – councils

Version 1.3 adds a switch to every detected controller that hides it from games and other apps through the [HidHide](https://github.com/nefarius/HidHide) driver. This document records the decisions, the architecture council and the design council for this feature.

## Feature decisions (made by the user)

| Question | Decision |
|---|---|
| Should the app hide controllers itself (replacing the 1.0 decision "HidHide hint only")? | Yes, one switch per detected controller |
| How long does a controller stay hidden? | Only while the app runs. Quitting makes it visible again; the next start hides it again. |
| How is HidHide installed if it is missing? | Button in the app, same secured flow as ViGEmBus. The first-run wizard stays unchanged. |

## Verified facts before the council

- HidHide's control device `\\.\HidHide` can be used **without administrator rights**. Only one process may hold it at a time.
- IOCTLs `CTL_CODE(32769, 2048..2055, METHOD_BUFFERED, FILE_READ_DATA)`: get/set application list, get/set device list, get/set active, get/set inverse mode. Lists are double-NUL-terminated UTF-16. Devices are listed by instance ID, applications by path in DOS device notation (`\Device\HarddiskVolumeN\...`).
- The device list is persistent. A "session" list that the driver clears itself when the process ends exists only in unreleased HidHide builds, not in the latest release 1.5.230.
- SDL only reports `XInput#<slot>` for Xbox controllers. On the development machine, the XUSB `GET_LED_STATE` IOCTL returned the player LED of the virtual controller ("player 1 on"), which maps an XInput slot to a device instance.

## Architecture council

Members: Claude Opus, Claude Sonnet, Claude Haiku. Each scored five proposals from 1 to 10.

| Proposal | Opus | Sonnet | Haiku | Result |
|---|---|---|---|---|
| A. Own small P/Invoke layer instead of the `Nefarius.Drivers.HidHide` NuGet package | 8 | 8 | 7 | Adopted (unanimous) |
| B. XInput slot to device via XUSB enumeration and player LED | 6 | 5 | 4 | Adopted with safeguards |
| C. Ownership and lifecycle | 6 | 6 | 6 | Reworked into a journal |
| D. Dedicated worker thread | 7 | 8 | 6 | Adopted, probing moved off the input thread |
| E. Hint that running games keep their handle | 8 | 9 | 7 | Adopted, wording widened |

### A. Access layer
The NuGet package pulls in an update-server client, logging abstractions and a device management library for eight IOCTLs. The app already pins and verifies everything it depends on, so a small own layer (`HidHide/HidHideClient.cs`) fits better. Rules from the council:
- Open the control device only briefly; retry with backoff when it is busy, with a bounded total time.
- Every list change is read-modify-write within one open session; size query first, then read with slack.
- If the program path cannot be converted to DOS device notation (for example on a network drive), nothing is hidden, so the app can never lock itself out.

### B. Mapping XInput controllers
This was the weakest proposal and received the most safeguards:
- All device probing runs on the HidHide worker, never on the input thread.
- The LED state is read twice and must match. Blinking or unknown states mean "unknown slot".
- Two devices on the same slot, or two controllers resolving to the same device, make the switch unavailable for both.
- **Own virtual controller:** a device under ViGEmBus in the virtual controller's slot is never hidden. ViGEm devices with an unknown slot are never hidden either. Without a reliably detected own controller, no XInput controller is mapped at all (fail-closed).
- ViGEm reuses instance IDs such as `...\01`. A saved ID could therefore point to the app's own virtual controller after a restart. Non-HID IDs are only hidden while the device is connected and mapped; HID IDs (`HID\...`) are unique and may be hidden in advance.
- Rejected: treating every ViGEm device as "ours". That would make it impossible to hide Sunshine's per-client controllers, which is a main use case.

### C. Ownership and lifecycle
- A journal (`%LOCALAPPDATA%\K26KControllerMerger\hidhide.json`) records what the app itself added: device entries, its own application entry, and whether it switched hiding on. It is written **before** each change.
- On quit, logoff and shutdown (`SessionEnding`) and on a terminating crash handler, exactly these entries are removed. After a hard crash, the next start cleans up from the journal.
- Entries that existed before, or were added by other tools or by hand in HidHide, are never removed.

### D. Threading
One worker thread (`HidHide/HideService.cs`) handles resolving, reading and writing. Changes are debounced (150 ms) and applied in one session. The UI reads immutable results.

### E. Running games
HidHide blocks new handles only. Games, Steam and other apps that already opened a controller keep seeing it until they are restarted. The overview says so in plain words.

### Round 1 findings and changes
- Disabled "Hide" switches gave no visible reason, and the HidHide card sat below the list. Now the "Hide" switch only appears when hiding works, the state card sits above the controller list, and a controller that can't be identified shows a visible caption instead of a dead switch.
- The setup card used jargon. It now leads with the benefit and has a caption about the download and the administrator prompt. The icon is an eye with a slash (composed, because the glyph is missing on Windows 10).
- The restart card had no action. It now has a warning tint, explains the consequence and offers "Restart Windows" with a confirmation dialog.
- "Restart" was ambiguous (Windows vs. game). The footnote now says to restart games and Steam that are already running.
- Labels and switches are aligned in two columns; the popup shows "Hidden" as a status tag like "Paused".
- Not changed: no warning on every visible controller ("may cause double input"). Most users select the virtual controller in the game; a warning on every row would be noise.
